# Implementation acceptance

These are future delivery criteria; none has been tested in setup.

- **C1 — Canonical creation/format.** Explicit create stages complete schema plus one identity, verifies, durably publishes then registers. Missing open refuses creation. Exact canonical table/column shape and format are enforced; numbered migrations, migration ledger and startup upgrades are absent. Fixtures cover complete creation, wrong shape/format/identity and interrupted publication.
- **C2 — Read-only refusal.** One structured verifier checks SQLite integrity, exact shape, identity, FK/relational invariants, reachable CAS hashes and configured activation/catalog consistency. Stable private inspection includes WAL/journal state before writable original open. Corruption/unsupported roots fail without source mutation, established with file manifests/hashes and WAL fixtures; verifier never repairs or salvages.
- **C3 — Ownership and mutation.** Closed/verifying/ready/failed admission gates writes; transaction entry and admission fence use one lock. Exclusive ownership and any observed ownership/integrity failure revoke writes/readiness until fresh verified open. Parallel-owner and race fixtures demonstrate refusal; domain updates and receipts commit atomically; CAS publication/rollback crash handling is deterministic.
- **C4 — Snapshot.** Owner mutation/GC barrier protects consistent SQLite and all referenced CAS copying. Candidate checksums and verification precede atomic durable publication. WAL-only committed content survives round trip; missing/bad CAS refuses; interrupted publication exposes no accepted partial snapshot; published snapshots remain immutable.
- **C5 — Replacement.** Verify snapshot, materialize fresh root, verify again, stop old owner and atomically switch catalog pointer. Retain damaged root. Issue fresh credentials and runtime epoch. Faults at materialization/publication/pointer switch leave a defined recoverable state; stale workers cannot reconnect. Use disposable owners/catalogs only.
- **C6 — Catalog and readiness.** Registration/selection lock covers the full read-modify-write operation. Concurrent processes do not lose unrelated registrations or advertise an unadmitted instance. Liveness stays distinct from readiness. Observed admission/ownership failure immediately revokes readiness; discovery is not database authority.
- **C7 — Consumer and removal parity.** Runtime, CLI, Astrid and packs use the single lifecycle boundary; typed HTTP errors and generated clients agree on success/error behavior. Representative existing domain flows pass. Remove schema_migrations, receipt backfills/migration proofs, allow_migration/strict_admission switches, identity-only exceptions, implicit create-on-open, tools/astrid_migrate, migration restore bindings, backup aliases, legacy_empty_inventory and duplicate lifecycle adapters within the identified dependency closure. Retain safety-bearing helpers and tests.
- **C8 — Safe cutover guidance.** Explicit operator provisioning produces a fresh development fixture realm. Documentation clearly rejects old realms/backups and describes verified replacement. Existing valuable/corrupt roots and backups are preserved untouched; physical corruption cause is not asserted. Record the preservation inventory and all final test/review evidence against the exact integrated candidate.
