## Push strategy

1. **Preservation inputs:** retain exact published refs plus a fresh manifest of later tracked/untracked deltas, with owner and inclusion/exclusion decisions. Astrid remote main advanced during snapshot publication while active local HEAD/index/dirty files were deliberately preserved. Runtime's preservation ref is not main. An automatic pull or replay of the old dirty patch can duplicate or lose the intended composition. [Source publication](../source-publication.md).
2. **Accepted continuation checkpoint:** publish a named continuation ref in each affected repository after P7/main/dirty reconciliation and affected validation; record the cross-repository manifest and retained input refs. Consumer managers start from that accepted source identity. This is the source-custody amendment already selected in [authority.md](../authority.md).
3. **Meaningful delivery checkpoints:** commit and normally push coherent tested candidate changes at contract/foundation or feature handoffs. Record candidate commit, dependency refs, relevant tests, owner and remaining gates. Use draft PRs where supported to expose reviewable changes early; a draft or pushed ref is not acceptance. Avoid pushing incomplete shared working trees or unrelated dirty files. Generated clients belong to the versioned producer contract handoff and are regenerated when consumers require them, then checked for final parity.
4. **Final integration candidate:** compose accepted changes, update each PR to the exact intended merge candidate and run affected combined checks. Freeze expected target-main heads alongside exact tested repository trees/SHAs and dependency/package identities; there is no atomic multi-repository Git merge. Stop the affected promotion on branch drift and revalidate the affected composition. Merge compatible producer/consumer changes in an explicit order through the repository's supported path, with main promotions coordinated by the integration owner. Project branch pushes can continue at accepted seams, but managers must not independently promote pieces of the final composition to main.
5. **Final main verification:** normally push/merge, fetch remote main identities, compare final trees with the tested composition, and run a small supported-entry-point smoke using those main revisions. If squash/rebase changes commit IDs, prove tree/dependency equivalence; if relevant bytes change, rerun affected checks. Publish the accepted final revision set only after every required merge is verified. Final report links PRs/commits and final cross-repository identities. No force-push, bypassed protection, deployment, or production cutover.

This supplies frequent recoverable progress without interpreting intermediate branch publication as permission to merge an unverified composition. The existing plan's finish instruction already requires final main/remote equality; checkpoints make that instruction operational. [Plan B/D](../plan.md).
