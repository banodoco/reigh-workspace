## Key decisions

- The existing `astrid serve` process becomes the sole persistence boundary for Reigh. Neither the browser nor workers may open SQLite directly.
- Extend the sanctioned bridge additively; preserve the frozen timeline routes unchanged.
- Reigh task creation remains a family-based HTTP contract. Move the 13 resolver implementations behind the bridge rather than duplicating them in the browser.
- Admit work into Astrid’s existing `tasks`, `task_dependencies`, `runs`, and `execution_attempts` tables. Do not create a second Reigh queue.
- Replace Reigh’s status-only claim model with Astrid’s fenced attempts: `attempt_id`, `lease_id`, `status_version`, heartbeats, expiry, and single-winner completion.
- Store generated bytes in Astrid’s content-addressed media tree. Store gallery/variant/shot-placement state in pack tables—not JSON files and not the kernel.
- Use polling initially: roughly 1–2 seconds while work is active, 5–10 seconds when idle, and the existing 30-second timeline polling.
- Cut credits, Stripe, Supabase auth/RLS, PATs, referrals, public sharing, hosted scaling control, and per-user tenancy for the local release.
- Migrate production data through an operator-only Postgres export plus receipt-keyed SDK replay. No importer becomes part of the product.
- Supabase may remain read-only during a rollback window, but it must not remain a runtime authority after cutover.

## 1. Overall approach

I agree with the prior-art posture on two points:

1. Postgres must not remain a second authority.
2. Migration machinery belongs under `Astrid/scripts/`, not in Astrid’s product CLI or kernel schema.

I disagree with “Reigh stays only an editor over the narrow timeline bridge.” That was valid when the goal was timeline editing. It is incompatible with the new goal: tasks, workers, generations, variants, shots, and media must also become Astrid-backed.

The target architecture is:

```text
Reigh browser ───────┐
Local/API workers ───┼── HTTP ──> astrid serve ──> SDK/repositories
Operator migration ──┘                         ├── SQLite
                                               └── managed media tree
```

The bridge remains one process and one writer queue, but gains separate adapters:

- Existing `TimelineBridgeAdapter`: unchanged.
- `[BUILD] ReighContentBridgeAdapter`: projects, shots, generations, variants, media.
- `[BUILD] ReighTaskBridgeAdapter`: task admission and task reads/cancellation.
- `[BUILD] ExecutorBridgeAdapter`: claim/start/heartbeat/stage/complete/fail.

Do not emulate PostgREST with a generic table API. Expose domain routes whose mutations call SDK/repository commands and preserve receipt, event, CAS, and same-project invariants.

For local-only security:

- Keep localhost binding, strict CORS, path containment, schema validation, content hashes, command idempotency, timeline CAS, attempt fences, the exclusive writer lock, and `executor_id` audit attribution.
- Cut Supabase Auth, RLS, service-role keys, PATs, `users`, credits UI, Stripe, public/anonymous sharing, referrals, rate-limit tables, and cloud worker scaling.
- Store provider secrets through environment/keychain resolution, never SQLite.
- If remote workers return later, that is a separate authenticated/TLS transport phase; do not weaken the local bridge now.

## 2. How tasks are created

### Concrete call path

```text
Reigh UI
  → createTask() in reigh-app/src/shared/lib/taskCreation/createTask.ts
  → AstridLocalClient.createTask()
  → POST /projects/{project_slug}/tasks
  → ReighTaskBridgeAdapter
  → ported family resolver
  → TasksService.create / RunRepository.create
  → core tasks + dependencies + receipt/event
```

Proposed request, intentionally close to today’s contract:

```json
{
  "family": "image_generation",
  "input": { "...": "existing family payload" },
  "materialized_inputs": [
    {"generation_id": "...", "kind": "file", "target": "source_image"}
  ]
}
```

Require an `Idempotency-Key` header. Return `201` for admission, `200` for replay, and `409 idempotency_mismatch` when the key is reused with different bytes.

The server ports the resolver registry currently in `reigh-app/supabase/functions/create-task/resolvers/registry.ts`. Unknown-family passthrough becomes a code-declared capability allowlist; the current `task_types` database is not migrated.

### Kernel shape

A resolved `wan_2_2_t2i` task should land approximately as:

```text
tasks.capability           = "reigh.wan_2_2_t2i"
tasks.spec_json            = {
  "schema_version": 1,
  "family": "image_generation",
  "source_task_type": "wan_2_2_t2i",
  "params": {...resolved worker payload...},
  "output_policy": {
    "create_generation": true,
    "shot_id": "...",
    "based_on_generation_id": null,
    "timeline_placement": {...}
  }
}
tasks.input_manifest_json  = [
  {"role": "style_reference", "media_id": "..."}
]
tasks.priority             = resolved priority
tasks.available_at         = now
tasks.max_attempts         = 3
tasks.status               = "queued" or "blocked"
task_dependencies          = one hard edge per dependant_on entry
```

Normalize incompatible task-type spellings in `capability`—for example `image-upscale` becomes `reigh.image_upscale`—while retaining the original string in `spec_json`.

Input media should resolve to Astrid `media_id`s during admission. The claim adapter may render those into bridge URLs or local paths expected by existing handlers. External model/LoRA URLs may remain URLs.

Batch families should be admitted atomically as a `run` with ordered child tasks. `[BUILD]` A public `RunsService.create` facade is needed because atomic fan-out exists in `RunRepository.create` but is not currently exposed by the SDK.

Initially, keep existing orchestrator contracts inside immutable task specs; replacing dynamic worker-created orchestration with fully structural runs is a later redesign.

## 3. How workers pick tasks up

Workers should poll the extended bridge. They must never access SQLite or Astrid repositories directly.

### Proposed worker protocol

- `POST /queue/claim`
  - Request: `executor_id`, supported `capabilities[]`, lease duration, idempotency key.
  - Response: task/spec/input manifest plus `project_id`, `attempt_id`, `attempt_no`, `lease_id`, `lease_expires_at`, `status_version`.
- `POST /tasks/{task}/attempts/{attempt}/start`
- `POST /tasks/{task}/attempts/{attempt}/heartbeat`
- `POST /tasks/{task}/attempts/{attempt}/outputs`
  - Streams output into attempt/lease-scoped quarantine.
- `POST /tasks/{task}/attempts/{attempt}/complete`
  - Supplies the staged output manifest and latest fence.
- `POST /tasks/{task}/attempts/{attempt}/fail`

Every state-changing request except heartbeat carries an idempotency key. Every attempt mutation carries `lease_id` and the latest `status_version`.

`[BUILD]` Extend `TaskRepository.claim` with a capability allowlist and a cross-project claim service. Its current claim is project-scoped and can select a capability the worker cannot run.

Use Astrid’s 300-second leases and heartbeat more frequently, e.g. every 30 seconds. Each heartbeat increments `status_version`; the worker’s lease keeper must serialize heartbeat with complete/fail so completion cannot submit a stale fence.

`[BUILD]` Run a maintenance loop in `astrid serve` that repeatedly calls `TaskRepository.expire_overdue`. Expiry already requeues within `max_attempts` and terminally fails exhausted work, but nothing currently schedules it.

### Worker code changes

Replace Supabase transports in:

- `reigh-worker/source/core/db/task_claim.py`
- `reigh-worker/source/core/db/task_status.py`
- `reigh-worker/source/core/db/task_polling.py`
- `reigh-worker/source/runtime/worker/guardian.py`
- `reigh-worker/source/media/video/storage.py`
- `reigh-worker-orchestrator/api_orchestrator/task_utils.py`
- `reigh-worker-orchestrator/api_orchestrator/storage_utils.py`

Keep `TaskRegistry` and the current WGP/VibeComfy handlers initially. Delete client-side retry counters and phantom-claim recovery; receipt replay and fenced attempts replace them.

Do not preserve today’s `complete_task` sequence, which uploads, creates generations, edits timelines, marks the task complete, and bills across separate operations. `[BUILD]` One Astrid completion service must, in one writer transaction:

1. Verify and prepare staged bytes.
2. Call `TaskRepository.complete`.
3. Insert `task_outputs`, `media`, `media_locations`, and lineage relations.
4. Create/update the generation projection.
5. Add the shot placement and optional timeline registry entry.

Bytes live in the managed media tree. `generations` and variants remain SQLite projections.

## 4. Work required for full Reigh-on-Astrid

### Reigh app

- `[EXISTS]` Keep `AstridBridgeDataProvider.ts` and the frozen timeline CAS behavior.
- `[BUILD]` Add `AstridLocalClient` modules for projects, content, tasks, and media; do not expand the video-editor `DataProvider` into an application-wide abstraction.
- `[BUILD]` Route `createTask.ts` and task cancellation/status hooks to the local client.
- `[BUILD]` Replace direct `supabase.from()`, RPC, storage, and edge-function calls with domain calls.
- `[BUILD]` Replace realtime subscriptions with React Query polling and active-work backoff.
- `[BUILD]` Replace Supabase upload/materialization with `POST /projects/{slug}/media`.
- `[CUT]` Auth gates, account settings, credits/ledger/Stripe, PAT management, referrals, public shares, and cloud worker dashboards.
- `[DECIDE]` Either port AI prompt/effect routes to local bridge proxies or hide those features. Persistent `timeline_agent_sessions` needs a pack table if retained.

### Bridge

- `[EXISTS]` Timeline discovery/load/save/CAS and Range/ETag timeline assets.
- `[BUILD]` Typed task, queue, content, and media routes in `local_bridge_server.py`.
- `[BUILD]` Add matching DTO schemas to `bridge_service.py`, the normative bridge contract, and `reigh-app/.../bridgeContract.ts`.
- `[BUILD]` General media serving route such as `GET /projects/{slug}/media/{media_id}/content`.
- `[BUILD]` Attempt-scoped staging, cleanup, request-size limits, typed fence errors, and lost-ack tests.

### Astrid schema and services

- `[EXISTS]` Core projects, tasks, dependencies, attempts, outputs, media, relations, receipts, events, runs, timelines, shots.
- `[BUILD]` Add a v2 migration to the shots/content pack containing:
  - `generations(id, project_id, task_id, type, name, based_on_generation_id, parent_generation_id, child_order, params_json, starred, created_at, updated_at)`.
  - `generation_variants(id, generation_id, media_id, variant_type, name, params_json, is_primary, starred, viewed_at, created_at)`, with one-primary-per-generation and unique media membership.
  - `shot_generation_items(id, shot_id, generation_id, timeline_frame, sort_key, metadata_json, created_at)`.
- `[BUILD]` Receipt-backed repositories/events for primary switching, starring, ordering, positioning, and deletion.
- `[BUILD]` Capability-aware claim, global queue summary, periodic expiry, atomic Reigh completion, and SDK fan-out admission.
- Do not add users, billing, worker-registry, task-types, importer, or legacy-alias tables.

### Production-data migration

- `[BUILD]` A SELECT-only Postgres/storage exporter using live production—not repo migrations—as ground truth.
- Export deterministic JSONL, source-row hashes, UUID/FK maps, storage manifests, and referenced bytes.
- Reuse `Astrid/scripts/migrations/v10/` patterns: dry-run, empty-target guard, exclusive lock, backup, deterministic IDs, SDK-only replay, and verification.
- Use keys such as `reigh-import:v1:generation:{source_uuid}`.
- Replay: projects → media → tasks/runs/dependencies/attempts/outputs → generations/variants → shots/placements → timelines/references.
- Drain workers before the final export. Never import an `In Progress` task as a live lease.
- Collapse timelines to their latest document; preserve the original event export as an immutable audit artifact rather than forging Astrid events.
- Verify counts, source hashes, media SHA-256, FKs, primary uniqueness, lineage, event chains, receipt replay, and representative app queries.

## Phase plan

1. **Contract and scope freeze.** Exit: feature cut list, capability map, pack DDL, HTTP schemas, and live-schema snapshot approved.
2. **Content foundation.** Build pack tables, repositories, media routes, and project/shot/gallery reads. Exit: Reigh browses and edits local projects without Supabase reads.
3. **Task admission.** Port all 13 families and golden-test the nine payload shapes. Exit: identical requests replay and batches commit atomically.
4. **Fenced worker path.** Add claim/start/heartbeat/stage/complete/fail and repoint both worker repos. Exit: representative WGP, VibeComfy, API, retry, crash-expiry, and cancellation workflows pass.
5. **Application cutover.** Remove remaining runtime Supabase calls and enable polling. Exit: no Supabase credentials or network requests are needed for supported local workflows.
6. **Data migration and cutover.** Warm export, maintenance freeze, final delta, replay, verify, switch. Exit: parity checks pass and Supabase is read-only rollback only.
7. **Retirement.** After the rollback window, remove Supabase adapters and obsolete edge/worker paths.

## Risks & blockers

- **Critical — remote workers:** localhost trust cannot serve RunPod/cloud workers. They are out of scope unless authenticated networking is added.
- **Critical — completion atomicity:** a task must not succeed unless bytes, media rows, generation projection, and placement all commit consistently.
- **High — slot-first history:** live `attempts`/`shot_slots` DDL and writers are not in the repos. Do not map them to kernel `execution_attempts`.
- **High — resolver drift:** 13 families and large compatibility payloads need fixture-based parity tests.
- **High — media volume:** bucket size is unknown; URLs may be missing or expired.
- **High — lease races:** heartbeat and completion must share one synchronized fence state.
- **Medium — polling load:** aggressive task polling may contend with the single writer unless reads stay read-only and responses are bounded.
- **Medium — timeline history loss:** latest-document migration intentionally omits foreign event history.

## Open questions for the owner

1. Are `attempts`/`shot_slots` authoritative product history, or may they be archived rather than imported?
2. Should production migration include all historical tasks/generations or only current projects and referenced media?
3. Are all workers guaranteed to run on the same machine for the local release?
4. Should storage migration import only referenced objects, or every object in `image_uploads`, `timeline-assets`, and `render-outputs`?
5. May public sharing, referrals, training-data management, and timeline-agent session history be explicitly removed from the local product?
6. Is latest-state-only timeline migration acceptable if the full Postgres event export is retained separately?
7. Is 1–2 second active polling acceptable, or is SSE required before cutover?
