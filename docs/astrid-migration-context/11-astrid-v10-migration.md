# 11 — Astrid v10 legacy-data migration: `scripts/migrations/v10/`

**Context doc for the Reigh→Astrid migration.** Describes the only existing migration machinery in Astrid: how `Astrid/scripts/migrations/v10/` replays the pre-kernel legacy file tree under `Astrid/projects/` into the v10 kernel SQLite (`Astrid/projects/.astrid/astrid.sqlite3`) — what it migrates, from which sources, the SDK-only idempotent-replay mechanism, what is dropped, its implementation status, and the resolution of the "v10 plan says NO data migration" contradiction. Read-only research; no repo files were modified. All claims grounded in repo files (paths cited inline); unobserved claims tagged **[INFERENCE]**.

## 1. Summary and key facts

The v10 migration is a **one-shot operator script set** that replays the pre-kernel legacy tree under `Astrid/projects/` into the v10 20-table kernel database using **only `AstridClient` + the SDK/repositories — no raw SQL writes and no importer tables** (`scripts/migrations/v10/MIGRATION.md:3-6`). It imports real projects (18), timeline containers + legacy timeline docs (62), referenced media (471 files, SHA-256 deduped, copied into the managed media tree), and completed generation/render runs (566 eligible of 806) as kernel runs + child tasks. The legacy tree is **never written, never archived, never deleted** — verify.py proves it is still on disk (read-only proof), and ~6,793 unreferenced media files (~8.5 GB) are only cataloged in `inventory.json` and left in place.

**Key facts (TL;DR)**

- **Sources consumed are files only** — `project.json`, `timelines/<ULID>/assembly.json` + `registry.json` + `display.json` (+ `assembly.jsonl` as provenance, never replayed), legacy `timeline.json`/`hype.timeline.json` + sibling `assets.json`/`hype.assets.json` docs, `runs/<run_id>/run.json` (+ `manifest.json`, `result.json`, `outputs/`/`inputs/` dirs for media refs), and referenced media bytes. **No Postgres/Supabase/Reigh source exists anywhere in Astrid** — there is no psycopg/asyncpg/PG driver, and the only Supabase code is a thin HTTP POST/RPC wrapper used by the Reigh bridge to *write* timeline events to Supabase (`astrid/core/timeline/eventlog/supabase_client.py:1-4`), not to import.
- **Mechanism: SDK-only idempotent replay.** Every mutation carries a stable receipt key `v10-migrate:{family}:{stable-id}`; the kernel command-receipt gates (`command_receipts` table) make reruns replay with zero new rows and a changed request under the same key fail as `idempotency_mismatch`. Object IDs are deterministically derived from the key (UUIDv5 via `derive_stable_id`; Crockford ULID via `derive_ulid`), so replays land on the same rows.
- **Pipeline:** `inventory.py` → `migrate_projects.py` → `migrate_media.py` (writes `media_map.json`) → `migrate_timelines.py` → `migrate_generations.py` (writes `migration_report.json`) → `verify.py`; orchestrated by `migrate_all.py` (dry-run by default).
- **Guards:** `--apply` refuses unless the kernel DB has **zero project rows**, refuses to clobber an existing `.bak`, requires the kernel exclusive-owner lock (stop `astrid serve`), and forbids concurrent migration processes (`MIGRATION.md:118-124`; `migrate_all.py:63-93`).
- **Status:** implemented and committed **2026-08-21** (`198976d9 feat(migration): v10 legacy-data migration scripts`, "Per Grok G2 design"; supporting kernel commit `ceeea24e feat(kernel): core.run.close + timeline.replace_config receipts (Grok-04)` the same day). **Not yet applied to any live DB** — the live kernel DB at `Astrid/projects/.astrid/astrid.sqlite3` has 0 rows in every table (4 `schema_migrations` rows only); no `.pre-v10-migration.bak`, `media_map.json`, or `migration_report.json` exists on disk. No committed tests reference the v10 scripts.
- **Contradiction resolution:** the v10 plan's "no data migration" (`unified-data-model-plan-v10-20260813.md:12,26-27,49-57`) is a *product-surface* commitment — no importer family, no importer tables, no compatibility/parity/cutover machinery, no old-authority writers. The scripts are **operator scripts outside the product** (under `scripts/`, not `astrid/`) that preserve the repo owner's actual legacy projects by replaying them *through* the product SDK. The product remains greenfield; `SKILL.md:154-155` and `docs/getting-started.md:41-44` now point to the scripts as the sanctioned legacy-data path.
- **Reigh relevance:** this is the closest machinery to moving Reigh data onto Astrid SQLite — the receipt-keyed SDK replay pattern, the inventory/reference-resolution walk, and the zero-child run-close trick all transfer directly. But a Reigh import would need a **new source adapter**: the v10 scripts read a local file tree, and nothing in Astrid reads Postgres/Supabase.

| Media bytes | any file under the project (excluding `.astrid/`, `.git/`, `node_modules/`, `__pycache__/`, `.DS_Store`) with a suffix in `MEDIA_EXTENSIONS` (`.png .jpg .jpeg .jfif .webp .gif .avif .tiff .tif .bmp .svg .mp4 .webm .mov .m4v .mkv .mpeg .mpg .mp3 .m4a .wav .aac .flac .ogg .opus .aiff .wma`) | only **referenced** files are hashed/imported; the rest are cataloged unreferenced (`inventory.py:39-62,384-450`) |

**No Postgres/Supabase/Reigh source.** Verified by grep across `Astrid/`: no `psycopg`/`asyncpg`/`pg8000`/`postgresql` anywhere in `astrid/` or `scripts/`. The v10 plan cuts Supabase append/timeline I/O and hosted worker from local GA (`unified-data-model-plan-v10-20260813.md:82,129`). **There is no existing code path that reads Reigh/Postgres data into Astrid SQLite.**

## 4. Import mechanism: SDK-only idempotent replay

**Writes go through the SDK/repositories exclusively** — `client.projects.create` (`migrate_projects.py:82-91`); `UnitOfWork(client.app.writer).run(...)` around `client.app.media.import_prepared`, `client.app.timelines.create`, `client.app.runs.create`, `client.app.tasks.claim/start/complete/fail`, `client.app.runs.close`, and `client.media.relate` (`migrate_media.py:66-108`; `migrate_timelines.py:107-160`; `migrate_generations.py:227-388`). `client.app` is the bound `StandardApplication` (repositories, events, writer; `astrid/sdk/client.py:118-119`). `AstridClient.open` acquires the kernel DB's exclusive-owner lock and fails closed when another owner holds it — "Stop `astrid serve` before `--apply`; do not run two migration processes concurrently" (`MIGRATION.md:118-124`; `client.py:79-90`).

**Idempotency — three cooperating layers:**

1. **Stable receipt keys.** `v10-migrate:{family}:{stable-id}` (`_common.py:18-36`):

   | family | key | stable id |
   |---|---|---|
   | project | `v10-migrate:project:{slug}` | directory slug |
   | media | `v10-migrate:media:{slug}:{sha256}` | byte SHA-256 |
   | timeline | `v10-migrate:timeline:{slug}:{ulid-or-path-hash}` | container ULID / 16-char SHA-256 of config path |
   | run | `v10-migrate:run:{slug}:{run_id}` | legacy run_id |

   Transition/derived steps use suffix keys: `:claim`, `:start`, `:complete`, `:fail`, `:relate`, `:id2` (cross-project run-id collision), `:slug2` (timeline slug conflict), and `v10-migrate:run-close:{slug}:{run_id}` (zero-child close; mirrors `core.run.close:{project_id}:{run_id}` scoping — `astrid/core/repositories/runs.py:152-154`).

2. **Kernel command receipts.** Inside each command's unit of work: `request_digest = request_hash(command_kind, request)` (canonical-JSON hash), then `ReceiptService.check(uow, project_id, idempotency_key, request_hash, command_kind)` — a receipt matching key+hash+kind returns the stored result (**replay, zero new rows**); same key with different hash/kind raises `ReceiptMismatchError`; none → proceed and `ReceiptService.record(...)` persists the receipt in the same transaction (`astrid/core/receipts/service.py:283-403`; command flow verified in `astrid/core/repositories/projects.py:353-439` and `media.py:814-829,1084-1098`). Receipts live in the kernel `command_receipts` table (v10 §2, `unified-data-model-plan-v10-20260813.md:147`).

3. **Deterministic object IDs.** `derive_stable_id(command_kind, scope, idempotency_key, ordinal)` = UUIDv5 over `\x1f`-joined components (`astrid/sdk/contracts.py:310-337`) — used for media ids (`migrate_media.py:60-62`). `derive_ulid(seed)` = SHA-256 → 26-char Crockford ULID (`_common.py:30-45`), mirroring `TimelinesService._derive_timeline_ulid`, used for derived timeline ULIDs, task ids, and derived run ids. Same key ⇒ same id ⇒ replay hits the same rows; the `:id2`/`:slug2` suffixed keys give collisions distinct deterministic identities.

**Inter-phase state files:** `inventory.json` (walk result, regenerable), `media_map.json` (referenced path → media id + prepared facts; `migrate_media` writes, timelines/generations/verify consume; migrate_media skips paths already present), `migration_report.json` (per-run fidelity path + task ids). Resume: re-run `--apply`; committed items replay under the same keys, remaining items proceed (`MIGRATION.md:88-94`).

**Legacy fidelity notes:** the legacy `run.json` is stuffed verbatim into the run's `input`; one evidence item `{kind: observation, data: {legacy_path, status, argv}}` records the migration (`migrate_generations.py:51-60`). `created_at`/`started_at`/`finished_at` are derived from `run.json` + `result.json` with `iso_max` clamping (`migrate_generations.py:390-410`). `assembly.jsonl` is never replayed as events — it is provenance inside `config._v10_migration` (`migrate_timelines.py:62-78`).

Run-failure semantics: if `complete` raises mid-fence, the attempt is terminally `fail`ed with error kind `migration_complete_failed` rather than left running (`migrate_generations.py:273-291`).

## 6. What's dropped / skipped

- **`agentic-*` test projects** (35) and their task-mode runs — excluded at inventory (`inventory.py:31,388-390`); their runs never enter the eligible set.
- **`builtin.agent_probe` runs** and any run with `status ∉ {completed, success}` or empty `run_id` (failed/running/skipped/cancelled) (`inventory.py:310-327`).
- **Unreferenced media** (6,793 files, ~8.5 GB per `MIGRATION.md:20-21`) — cataloged only, stays on disk, never hashed.
- **Non-media referenced files** — `NON_MEDIA_NAMES` (run.json, plan.json, tool-run.json, manifest.json, result.json, preview.json, metadata.json, assets.json, timeline.json, hype.*, assembly.*, registry.json, display.json) plus any suffix outside `MEDIA_EXTENSIONS` (`_common.py:52-73`).
- **Unresolvable media references** (210 in the current inventory) — missing files, remote URLs (`http/https/ftp/s3/gs`), inline `data:` URLs, ambiguous basenames; recorded with a `note`, dropped (`_common.py:97-138`).
- **Repo-root data** — root-level `runs/`, `sessions/`, identity, `cli-usage.jsonl`: the walk only iterates per-project dirs under the root, so anything outside `projects/<slug>/` is never seen (`inventory.py:384-392`).
- **Timeline history/event chains** — `assembly.jsonl` (and by extension head/checkpoint/identity files) is provenance, never replayed; no legacy event/hash-chain translation (`MIGRATION.md:10-11`; v10 plan CUT rows for assembly chains, `unified-data-model-plan-v10-20260813.md:52`).
- **Run event/audit chains** — `runs/*/events.jsonl`, `audit/ledger.jsonl` are not read at all (v10 plan: "No run dialect, event-chain, or audit-ledger import survives", `:118`). The kernel records only the condensed observation evidence.
- **Project semantics** — `sources.json`, per-source `source.json`, experiments product state, `.astrid.variants.json`, threads, plan.json, sessions, leases: not imported (plan CUT/DEFER rows `:51,83,120,123`); their **media bytes** can still enter via `media import` or the referenced-media walk.
- **Supabase/editor-FSA data** — never a source (plan `:82,129,134`).

Net effect: the migration is **import (referenced subset) + leave-in-place (everything else)** — nothing is archived to a new location and nothing is deleted. `verify.py` asserts legacy files are still on disk as a read-only proof (`verify.py:168-187`).

## 8. Plan-vs-code contradiction resolution

**The contradiction:** the v10 plan is explicit that there is no data migration — "Old project, timeline, run, thread, session, plan, lease, event-chain, audit-ledger, Supabase, and editor FSA authorities are **not migrated or conditionally supported**" (`unified-data-model-plan-v10-20260813.md:12`); the multi-source importer is deleted (`:27,49`); `project.json`/assembly chains/run.json dialects are CUT "neither read nor migrated" (`:117-118`); the sprint plan commits "no production users or legacy data must be migrated, consistent with v10 §1" (`astrid-first-sprint-plan-20260813.md:35`); `NORTHSTAR.md:41`: "No legacy data import beyond `media import` (bytes only). No project/history/run-dialect/timeline-chain/audit import, no aliases, no parity/cutover machinery." Yet `scripts/migrations/v10/` exists and imports projects, timelines, runs, and media.

**Resolution (evidence-grounded):** the plan's prohibition is about the **product surface and the schema**, not about operator scripts:

1. The plan's targets are product machinery: an importer *family*, importer *tables* (the 20-table catalog has none), compatibility/parity/cutover *programs* (v9's five-boundary continuity harness), and old-authority *writers*. The v10 scripts violate none of these: they add zero tables (the kernel DB still has exactly the 20 v10 tables), they write **only** through the product SDK/repositories (the exact boundary the plan mandates, `:651` "repositories are the only semantic writers"), and they are not a product CLI family — they live under `scripts/` (`MIGRATION.md:3-6`; `migrate_all.py:1-25`).
2. The scripts are a **personal data rescue** for the repo owner's real legacy tree (18 non-`agentic-*` projects, 566 completed runs, ~471 referenced media files) that postdates the plan: both commits landed 2026-08-21, the same day the kernel grew the `core.run.close` receipt needed by the zero-child path. The design attribution "Grok G2" appears only in code comments and the commit message (`_common.py:17-19`; `198976d9` body) — no separate design doc is committed.
3. The docs were updated in the same work to make the scripts the *sanctioned* legacy path: `SKILL.md:154-155` and `getting-started.md:41-44`. So the current, operational position is: **greenfield product, no importer in the product, and a scripts-level SDK replay for the user's own legacy data** — the plan's "no migration" was never revoked, it was scoped to product machinery; the scripts sit outside that scope.
4. What the migration does with legacy data: **import** the referenced/migratable subset into the kernel (projects/timelines/media/runs), **leave in place** everything else (unreferenced media, ineligible runs, root-level state, sources/experiments files). It does **not** archive legacy data into a new structure and does **not** delete it — `verify.py` proves the legacy tree remains on disk (`verify.py:168-187`), and the legacy tree is "never written" (`MIGRATION.md:6`).
5. Precedent: the v7 plan had proposed a disposable `astrid bootstrap import <project-path>` ("idempotent by an input-manifest request hash", `unified-data-model-plan-v7-20260813.md:693`); the v10 scripts realize that same idea outside the product, consistent with v10's "treat current Astrid as a source-code parts bin, not a data source" posture (`:727`).
