## 1. Summary + key facts

Reigh's task queue is a **status-machine lease, not a lock**. A task is "leased" by the atomic `UPDATE tasks SET status='Queued'→'In Progress', worker_id=…` inside `claim_next_task_service_role`; there is no lease-expiry column or TTL — liveness is inferred from `generation_started_at`/`updated_at` age and recovered by three independent sweeps (5-minute cron `auto_fail_stale_tasks`, heartbeat crash-recovery, orchestrator startup reset). Retries are counted on `tasks.attempts` (integer, max 3) and executed by *re-queuing* the same row (worker-side retryable-error classification or heartbeat `crashed` recovery); there is no separate execution-attempt ledger for tasks. The `attempts` **table** (84k rows live) is a different thing entirely: the **slot-first media-generation attempt model** (one row per render attempt of a `shot_slots` slot, `task_id` nullable) that was applied to prod **outside the migration ledger** (no repo migration and no `schema_migrations` entry creates it — a real drift gap in doc 07's "no reverse drift" claim).

Key facts:

- **Live claim surface** (prod, `pg_proc`): `claim_next_task_service_role(p_worker_id text, p_include_active boolean, p_run_type text, p_same_model_only boolean, p_max_task_wait_minutes integer, p_worker_pool text, p_task_types text[])` — 7-param, SECURITY DEFINER, returns `(task_id, params, task_type, project_id, user_id)`. A legacy 3-param overload also exists but is dead code.
- **Prod reverted the route-gating claim**: the repo's final claim/count functions (May 6–13) gate on `route_backend_claim_decision` and write `claimed_backend`/`claimed_route_key`/`claim_decision_snapshot`; the **live** functions do **not** (no route gating, no claim-decision columns written). Four prod-applied migrations absent from the repo explain this (see §5).
- **`tasks_assert_claimable` trigger is DROPPED in prod** (2026-05-24, `20260524010000`); the function remains orphaned. Live `tasks` has only 2 triggers: `prevent_timing_manipulation_trigger`, `trigger_bill_cancelled_orchestrator`.
- **Retry model**: `tasks.attempts` incremented only on requeue paths; cap = 3 (`attempts < 3` requeue, `>= 3` terminal fail). Live distribution: 46,007 tasks with attempts=0, 17 with attempts=1, **zero with ≥2** — retries are rare in practice.
- **`sentinel_ticks`** (144,101 rows, 2026-05-13 → 2026-08-21, ~1/min): written by edge fn `route-contract-sentinel`, triggered by pg_cron job of the same name. State distribution: `UNCLAIMABLE_WORK` 93,433 (65%), `NO_WORK` 30,993 (22%), `OK` 18,599 (13%), `WORKERS_STUCK_INITIALIZING` 1,046, `NO_READY_WORKERS` 30. **`pause_scaling` has a live row right now** (`production`, `UNCLAIMABLE_WORK: 1/3 probed queued tasks unclaimable`, until 2026-08-21T16:25Z) — scaling is paused as of this writing.
- **Capacity today**: live gpu orchestrator scales from `task-counts` edge-fn numbers (`queued_only`, `blocked_by_capacity`, `potentially_claimable = queued_only + blocked_by_capacity`), bounded by `min_active_gpus`/`max_active_gpus`, with `machines_to_keep_idle` buffer and `ready_for_tasks` promotion. The **capacity-reconciler variant** (`worker_capacity_intents`, `worker_capacity_route_backoffs`, `orchestrator_leases`, shadow/authoritative modes) is **not deployed** — no such tables in prod.
- **Current live state**: 46,024 tasks (`Complete` 27,392 / `Cancelled` 14,678 / `Failed` 3,939 / `Queued` 15 / `In Progress` **0**); attempts 83,872 (`complete` 82,557 / `failed` 1,315); workers 6,878 `terminated`, 43 `error`, 16 `inactive`, 2 `active`; no `banodoco_*` task types seeded.

## 2. claim_next_task deep-dive (live 7-param algorithm)

Source: live `pg_get_functiondef` of `public.claim_next_task_service_role(text, boolean, text, boolean, integer, text, text[])` (dumped to `/tmp/live_claim_fn.txt`); caller: `reigh-app/supabase/functions/claim-next-task/index.ts` (service-role path). Repo ancestors: `20260504120000_extend_claim_next_task_for_pools.sql` (identical except live adds a NULL-safe `v_is_banodoco_pool := (COALESCE(p_worker_pool,'') = 'banodoco')`), which itself descends from `20251222000001_add_same_model_only_param.sql`, `20260121000000_support_multiple_dependencies.sql`, `20260121170000_fix_claim_preserve_generation_started_at.sql`.

### 2.1 Signature & parameter semantics

| Param | Default | Meaning |
|---|---|---|
| `p_worker_id text` | — | worker id stamped into `tasks.worker_id`; also looks up `workers.current_model` (only if `status='active'`) |
| `p_include_active boolean` | false | false → only `Queued`; true → also considers `In Progress` (only used by count dry-runs; the final `UPDATE` still requires `tasks.status='Queued'` unless true) |
| `p_run_type text` | null | null = no filter; else `get_task_run_type(t.task_type) = p_run_type` |
| `p_same_model_only boolean` | false | true → prefer tasks whose `get_task_model(params)` = worker's `current_model`; bypassed when no matching tasks exist or a task is "starving" |
| `p_max_task_wait_minutes int` | 5 | starvation threshold: any eligible task with `created_at < now() − max_wait` flips ordering to pure FIFO |
| `p_worker_pool text` | null | `'banodoco'` → only `task_type LIKE 'banodoco\_%'`; non-null/other → excludes `banodoco\_%`; null → no pool filter |
| `p_task_types text[]` | null | non-empty → `task_type = ANY(p_task_types)` allow-list, layered on pool/run_type filters |

### 2.2 Algorithm walkthrough (plpgsql, single statement)

1. **Guard-ish validations** (no `route_backend_claim_decision`, no backend/namespace validation — reverted in prod, see §5):
   - `v_status_filter` from `p_include_active` (dead in the final UPDATE, legacy of count semantics).
   - `v_worker_model` := `workers.current_model` for `id=p_worker_id AND status='active'` (null if worker unknown/inactive).
2. **`_eligible_users` temp table** (`ON COMMIT DROP`): one row per user where
   - `credits > 0`, and `settings->'ui'->'generationMethods'->>'inCloud'` coalesced to true (cloud allowed), and
   - `COUNT(in_progress_tasks)` over their projects' tasks with `status='In Progress'` and `task_type NOT ILIKE '%orchestrator%'` **< 5** (per-user concurrency cap of 5, orchestrator tasks excluded from the count).
3. **Starvation pre-scan** (only when `p_same_model_only` AND worker has a model): over queued, deps-complete, eligible-user tasks matching run_type + pool + task_types filters, compute
   - `v_no_matching_tasks` := no task matches the worker's model, and
   - `v_has_starving_task` := any task `created_at < now() − max_task_wait_minutes`.
4. **`ready_tasks` CTE + atomic UPDATE** (the claim):
   - Candidates: `status='Queued'`, `all_dependencies_complete(t.dependant_on)` (multi-dep unnest helper, from `20260121000000`), user ∈ `_eligible_users`, run_type filter, pool/task_types filters.
   - Ordering: `ROW_NUMBER() OVER (ORDER BY CASE WHEN starving/no-matching THEN NULL WHEN worker model matches THEN 0 ELSE 1 END NULLS LAST, created_at ASC)` — i.e., model-affinity first, then FIFO; starvation (or no matching tasks) forces pure FIFO `created_at ASC`.
   - `UPDATE tasks SET status = CASE WHEN status='Queued' THEN 'In Progress' ELSE status END, worker_id = CASE WHEN status='Queued' THEN p_worker_id ELSE worker_id END, updated_at = NOW() (only when Queued), generation_started_at = NOW() (only when Queued) FROM ready_tasks rt WHERE tasks.id = rt.id AND rt.rn = 1 AND (NOT p_include_active OR tasks.status='Queued')`, then `RETURNING` into local vars and `RETURN NEXT`.
5. **Output**: `task_id, params, task_type, project_id, user_id`. Note: the live version returns **none** of the route fields (`claimed_backend`, `route_key`, `claim_decision_snapshot`, …) that the repo's May-6/7 versions returned; the worker's `_claim_route_guard` (`reigh-worker/source/core/db/task_claim.py:113-155`) therefore sees `claimed_backend IS NULL AND selected_backend IS NULL AND claim_reason IS NULL` → **guard short-circuits to "let it run"** (its comment says this is for "older task responses" while the route-aware DB migration is deployed — which prod then reverted).

### 2.3 Locking / lease / reentrancy semantics

- **Lease = status flip + worker_id stamp.** There is no `leased_until`/TTL column; `generation_started_at` is the implicit claim timestamp. Reclaimability is only ever restored by the recovery paths in §8, never by an expiry predicate in the claim query.
- **No `FOR UPDATE SKIP LOCKED` in the live 7-param function.** The claim is a single `UPDATE … FROM (CTE) WHERE rn=1`. The old 3-param overload (live, dead) *does* use `LIMIT 1 … FOR UPDATE SKIP LOCKED` (`/tmp/live_claim_3param.txt`); the SKIP LOCKED lineage runs `20250113000004_update_claim_functions_for_timing.sql` → `20250914000004` (PAT) → `20260121170000_fix_claim_preserve_generation_started_at.sql` — and that last one also carried a `AND tasks.status='Queued'` re-check in the UPDATE WHERE, which is the proper double-claim guard. `20260504120000_extend_claim_next_task_for_pools.sql` (repo, applied) dropped both the SKIP LOCKED and the status re-check, and the live function inherits that. Because the CTE contains the volatile plpgsql helper `all_dependencies_complete`, it stays materialized (PG 12+ inlining rule); under concurrent claims of the same head-of-queue row, the second transaction blocks on the row lock, then its EPQ re-check passes (its WHERE only references `tasks.id` + frozen CTE columns + `NOT p_include_active`, all still true) and it **returns the same task_id with a no-op status/worker write** — a genuine double-claim window. [INFERENCE from SQL text; not empirically reproduced (read-only constraints). In practice the window is small (staggered polls, model-affinity ordering), and worker-side dedup is absent for service-role claims (`check_my_assigned_tasks` is a PAT-era no-op).] This is a real primitive-quality gap worth noting for the Astrid migration: use `FOR UPDATE SKIP LOCKED` (or a status re-check on the current row) as the claim primitive.
- **Atomicity**: single statement = single snapshot; concurrent claims of *different* head rows are safe (each UPDATE locks only its target row).

## 3. attempts / retry model

### 3.1 `attempts` table = slot-first media attempts (NOT task retries)

- Live columns (`07-live-db-schema.md:116-154`): `id uuid PK`, `slot_id uuid NOT NULL` (FK `shot_slots`), `project_id uuid NOT NULL` (denormalized, trigger-kept), `task_id uuid NULL` (FK tasks, `ON DELETE SET NULL`), `params jsonb` (+ derived `params_prompt`/`params_seed`/`params_model` generated columns), output/storage fields (`output_url/bucket/path`, `thumbnail_*`, `storage_mode attempt_storage_mode default 'remote'`, `local_*`), `status attempt_status default 'queued'` (lowercase enum: `queued|in_progress|complete|failed|cancelled`), `attempt_type attempt_type default 'original'` (`original|regen|edit|upscale|reposition|duplicate`), lineage fields (`based_on`, `parent_attempt_id`, `child_order`, `pair_shot_attempt_id`), `starred`, `name`, `error_message`, `viewed_at`, `superseded_by`, `deleted_at`, timestamps.
- **Semantics**: one row per *render/generation attempt of a shot-local slot* — the "slot-first redesign" (`reigh-app/.megaplan/_archived_slot-first-m1-schema-idea.md`, `how-to-follow-along.md`: "replace legacy `generations`/`generation_variants`/`shot_generations` with `shot_slots` + `attempts`", running as a 7-milestone megaplan chain). `task_id` is nullable and many-attempts-per-task is allowed ("one task → many attempts allowed for retries", `slot-first-m1-foundations-idea.md:25`). Attempts are append-only history; the "current" attempt is `shot_slots.primary_attempt_id`.
- **Writers**: 26 live `slot_first_*` RPCs (`slot_first_create_pending_attempt`, `slot_first_mark_attempt_in_progress`, `slot_first_complete_attempt`, `slot_first_fail_attempt`, `slot_first_promote_attempt`, `get_attempt_lineage`, …). **No caller of any `slot_first_*`/`shot_slots` exists in `reigh-app/supabase/functions`, `reigh-app/src`, `reigh-worker/source`, or `reigh-worker-orchestrator`** — the chain's caller-migration milestones (M2–M4) are not in this checkout. The table's 84k rows (82,557 complete / 1,315 failed; no queued/in_progress rows live) are backfilled + dual-written history (`slot_first_migration_map` 121k rows is the migration mapping table).
- **Live but untracked**: **no repo migration and no `supabase_migrations.schema_migrations` entry creates `attempts`, `shot_slots`, the `attempt_*`/`shot_slot_kind` enums, or the `slot_first_*` functions/triggers** (verified by grep over `reigh-app/supabase/migrations/` and a live query of `schema_migrations` for 202605–202606 versions). The DDL was applied to prod directly from the megaplan chain. This contradicts doc 07's "no reverse drift: every live table maps to an applied migration" — a gap to fix in the migration ledger. 11 CHECK constraints on attempts (lineage acyclicity, storage identity, terminal-has-output) are all live (see §5.3 list from `pg_constraint`).

### 3.2 Task-level retry: `tasks.attempts` (integer, cap 3)

- Column: `tasks.attempts int NOT NULL DEFAULT 0` (added by `20250202000000_add_missing_columns.sql`; comment in worker debug: "attempts is task-level retries (re-claimed / re-processed), not internal HTTP retries" — `reigh-worker/debug/formatters.py:169`).
- **Incremented only on requeue paths** (never on first claim):
  1. **Worker-side retryable-error requeue** (`reigh-worker/source/task_handlers/worker/fatal_error_handler.py:97-160` + `runtime/worker/server.py:939-976`): after a task fails, `is_retryable_error(error_message)` classifies against `RETRYABLE_ERROR_PATTERNS` (`generation_no_output` max 2; `edge_function_transient` max 3; `network_transient` max 3; default 2; OOM explicitly **not** retryable). If retryable and `current_attempts < max_attempts` → `requeue_task_for_retry(task_id, msg, current_attempts, category)` → `update-task-status` edge fn with `status:'Queued'`, `attempts: current+1` (falls back to direct DB `requeue_task_direct_db`); else → mark Failed. In-progress→Queued is an allowed transition (`update-task-status/transitions.ts`: `'In Progress': ['Complete','Failed','Cancelled','Queued']`).
  2. **Heartbeat crash recovery** (`20260331060000_add_crash_recovery_to_heartbeat.sql`, live body verified): when guardian reports `status_param='crashed'` (worker `guardian.py:165` detects the worker process died), all that worker's In-Progress tasks get `status='Queued', worker_id=NULL, generation_started_at=NULL, attempts+1, error_message='Requeued: worker crashed (attempt N)'` **if attempts < 3**; those with attempts ≥ 3 get `Failed` + `cascade_task_failure` propagation.
  3. **API orchestrator startup reset** (`reigh-worker-orchestrator/api_orchestrator/database.py:68-108`): at boot, tasks In-Progress on its worker_id are requeued with `attempts+1`, `error_message='Reset on startup - orphaned from worker restart (attempt N/3)'`, guarded `.lt('attempts', 3)`.
  4. **Claim-time route mismatch** (`reigh-worker/source/core/db/task_claim.py:86-110`): `_requeue_backend_mismatch` / `_fail_closed_claim_decision` requeue with `error_category='backend_mismatch'` (currently inert because the live claim fn returns no route fields — §2.2.5).
- **Max-attempts constants**: heartbeat crash → 3; api orchestrator startup → 3; worker retryable categories → 2–3; old `func_mark_task_failed(uuid, text)` (dead) used `>= 3 → 'Failed' else 'Error'` — `'Error'` is **not a valid `task_status` enum value**, so that overload errors at runtime and is dead code.
- **Live distribution** (prod query): attempts=0 → 46,007; attempts=1 → 17; attempts≥2 → 0. Retry is essentially unused in production today.
- **Terminal statuses**: `Complete` (via `complete_task` edge fn → `func_mark_task_complete` or direct `update-task-status` Complete), `Failed` (via `update-task-status`/`func_mark_task_failed(text,text)` live body: sets status/error_message/generation_processed_at), `Cancelled` (via `update-task-status`; `trigger_bill_cancelled_orchestrator` bills completed segments of a cancelled orchestrator — `20260112140000_add_orchestrator_cancel_billing_trigger.sql` + `cancellationBilling.ts`). No transitions out of terminal states (`transitions.ts`).

## 4. sentinel_ticks semantics

- **Schema** (live): `ts timestamptz PK default now()`, `state text NOT NULL`, `detail jsonb`; one unique index on `ts` (`07-live-db-schema.md:464-471,1133-1136`).
- **Producer**: pg_cron job `route-contract-sentinel` (`* * * * *`, scheduled by `20260513120300_sentinel_infra.sql`) → `net.http_post` to edge fn `https://wczysqzxlwdndgxitrvc.supabase.co/functions/v1/route-contract-sentinel` with a service-role JWT read from Vault (`vault.decrypted_secrets` name `sentinel_service_role_jwt`) → edge fn (`reigh-app/supabase/functions/route-contract-sentinel/index.ts`) classifies and inserts one `sentinel_ticks` row.
- **Classification** (edge fn logic): load ≤500 Queued tasks (including orchestrators — deliberately, because the breakdown RPC excludes them and "blinded the orchestrator's lifecycle safety net"), ≤500 workers with `status IN ('active','spawning')`; then:
  - `NO_WORK` — no queued non-orchestrator tasks;
  - `UNCLAIMABLE_WORK` — any probed queued non-orchestrator task (cap 25 probes; probes `route_backend_claim_decision` per `selected_backend` or both backends; missing `route_key` counts as unclaimable) is not eligible;
  - `WORKERS_STUCK_INITIALIZING` — any `active` worker without `metadata.ready_for_tasks` or `spawning` worker with heartbeat/starter older than 30 min;
  - `NO_READY_WORKERS` — no `active` worker with `metadata.ready_for_tasks === true`;
  - else `OK`.
- **Alarm**: after inserting the tick, if state ∈ {`UNCLAIMABLE_WORK`, `WORKERS_STUCK_INITIALIZING`} and the 5 most recent ticks (including this one) are all the same alarm state → POST `SENTINEL_WEBHOOK_URL` (Discord-style `{text, state, detail}`) and `upsert pause_scaling (pool='production', until=now()+30min, reason=…)`.
- **`pause_scaling`** (schema in `20260513120300_sentinel_infra.sql`): `pool text PK, until timestamptz NOT NULL, reason text`; orchestrator is expected to skip scale-up while `until > now()`. **Live row exists right now** (queried 2026-08-21 ~16:00Z): `production | 2026-08-21 16:25:01Z | UNCLAIMABLE_WORK: 1/3 probed queued tasks unclaimable` — the sentinel paged and scaling is paused at time of writing.
- **Reader**: `reigh-worker-orchestrator` health code (docs/03 covers) plus the paging/`pause_scaling` consumer; the gpu orchestrator's `database.py`/`control_loop.py` read `pause_scaling` to suppress spawns (per the migration comment: "Orchestrator reads this and skips scale-up when until > now()"). [INFERENCE — the exact pause_scaling read call site wasn't located in this pass; grep `pause_scaling` in orchestrator repos came back clean, so the consumer may live on the Railway-deployed branch.]
- **Volume**: 144,101 rows over 2026-05-13 13:41 → 2026-08-21 15:55 (≈100 days) ≈ 1,441/day ≈ 1/min with occasional extra ticks. The dominant state is `UNCLAIMABLE_WORK` (65%) — i.e., since the sentinel shipped, the queue has mostly been judged unclaimable (the route-contract gating era and its aftermath).

## 6. Capacity-reconciler intent vs live reality

### 6.1 Live capacity measurement (deployed today)

- **`task-counts` edge fn** (`reigh-app/supabase/functions/task-counts/index.ts`): service-role path runs 4 RPCs in parallel — `count_eligible_tasks_service_role(false, run_type)`, `count_eligible_tasks_service_role(true, run_type)`, `count_queued_tasks_breakdown_service_role(run_type)`, `per_user_capacity_stats_service_role()` — and returns `queued_only`, `active_only`, `blocked_by_capacity`, `blocked_by_deps`, `blocked_by_settings`, `potentially_claimable = queued_only + blocked_by_capacity`, plus filtered task lists (per-user 5-cap, credits>0, inCloud, deps complete, run_type).
- **`gpu_orchestrator` control loop** (`reigh-worker-orchestrator/gpu_orchestrator/control_loop.py:197-218`, `database.py` aggregates per-route `selected_pool_totals`): `queued_count = potentially_claimable`, `total_tasks = potentially_claimable + active_cloud_count`; scaling decision (`control/phases/scaling_decision.py:76-105`): `desired = clamp(max(min_active_gpus, task_based, busy + max(machines_to_keep_idle,1)), max_active_gpus)`; spawn when `current_capacity < desired` and failure-rate OK; terminate idle when above. Workers register via `func_update_worker_heartbeat` / `func_worker_heartbeat_with_logs`, publish `metadata.ready_for_tasks` (worker `server.py` `_publish_preflight(…, ready_for_tasks=True)`), and get promoted `spawning→active` on `ready_for_tasks` (`control_loop.py:459-464`). Route contract of each worker (backend/profile/pool/selector namespace/version/contract) is compared against the pool's expected route before counting it (`worker_state.py` route-match helpers).
- **Sentinel interplay**: `pause_scaling` (from §4) is the only DB-level capacity brake today; `UNCLAIMABLE_WORK` pages have been firing since May and pause_scaling is currently set.

### 6.2 Capacity-reconciler variant (design intent, NOT live)

Repo `reigh-worker-orchestrator-capacity-reconciler/` (a separate variant tree; shares `gpu_orchestrator/` + `api_orchestrator/` code with the main orchestrator plus a new `control/capacity_reconciler.py` etc.). SQL: `sql/20260514000000_create_worker_capacity_intents.sql` (never applied — no such tables live; confirmed by 07 doc §4.4 and live query).

- **`worker_capacity_intents`**: per-(pool, cycle) durable intent rows — `desired_capacity int >= 0`, `reason`, observed counters (`observed_queued/active/spawning/idle/in_progress/route_stale`), `effective_capacity`, `cycle_id`, `observer_id`, `actions jsonb` + `suppressed_actions jsonb`, `outcome jsonb`, `valid_until`, `stable_since`, `consecutive_spawn_failures`, `next_spawn_allowed_at`, `shadow boolean default true`. Unique authoritative row per `(pool, cycle_id)` when `shadow=false`.
- **`worker_capacity_route_backoffs`**: per-(pool, route_key) spawn backoff (`consecutive_spawn_failures`, `next_spawn_allowed_at`, last success/failure timestamps); `__pool_floor__` sentinel key for pool-floor backoff.
- **`orchestrator_leases`**: `lease_key PK, pool, holder_id, acquired_at, expires_at, metadata` — distributed lease so only one authoritative reconciler acts per pool.
- **Loop** (`control/capacity_reconciler.py`): `reconcile(cycle_id)` = observe → plan (`build_capacity_plan` on `min_active_gpus`/`max_active_gpus`/`machines_to_keep_idle`/poll_sec) → admit → record intent (`record_pre_act`, shadow or authoritative) → act (`SPAWN` / `CANCEL_PENDING_SPAWN` / `TERMINATE_IDLE` / `NOOP`) → record outcome. Shadow mode logs intended actions to `system_logs` only; authoritative mode acquires the pool lease, records `shadow=false` intent, executes, resets/records route backoffs per spawn outcome, releases lease. Route-aware observation uses `selected_pool_route_filter()` and `potentially_claimable` counts (same task-counts contract as live).
- **How it would feed task claiming**: intents/backoffs gate *worker spawn/terminate*, not the claim RPC itself; claimability still comes from `claim_next_task_service_role`. The design's `route_key`-scoped observations anticipate route-gated claims (which prod reverted — see §5.2), so the variant's route-aware premise is currently inconsistent with live claim behavior.
