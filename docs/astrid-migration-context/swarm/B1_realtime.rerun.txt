# B1 — Local realtime design for Reigh-on-Astrid (evidence memo)

## Verdict

Replace Supabase Realtime with **adaptive polling**, not SSE/WebSocket. Timeline: keep the existing **fixed 30 s bridge polling + CAS 409** untouched. Tasks/generations/status: **cursor-aware adaptive polling — 2 s while active work exists, 10 s idle, 30 s gallery** (ratified doc 15 Q7, doc 20 §18.8). Reject push: single writer on loopback, no correctness gain, no notify hook exists server-side. Do not build on SDK `subscribe_events` — it is Python-only, poll-based, and reads the legacy file store, not the kernel.

## Recommended mechanism/cadences

**(1) Timeline edits/sync/divergence** — fixed polling, unchanged: 30 s doc+registry (`useTimelineQueries`), 3 s discovery while bridge down (`useAstridBridgeDiscovery`). Conflicts stay CAS 409 → `tryRecoverLostAck` reload-ack; poll adoption already rejects mid-edit/own-echo polls. Cut spoke/hub bookmarks, keep-both artifacts, `app-bookmark`/`app-divergence`, and the divergence dialog — those are multi-device semantics (doc 20 §13.7); a single local writer plus 409+draft-recovery fully covers it. Keep `reigh.timeline-drafts` for crash recovery.

**(2) Tasks/runs/generations/status** — adaptive polling with cursor. Foreground: **2 s** for active-work queries (pending generations/segments, active clips, status counts, run progress — driven by "client has queued/running work"), **10 s** idle, **30 s** gallery/project reads. Background: pause non-active polls (keep `refetchIntervalInBackground` only for active-work), rely on `refetchOnWindowFocus` + 30 s cadence. Reconnect: bridge-down → existing 3 s health poll + smart-poll max 15 s for data; on healthy, full refetch and resume from last `project_seq` cursor. Failure: save backoff 500→8000 ms + watchdog banner (existing). Cursor primitive: kernel `events.project_seq` is gap-free and monotonic (doc 04 §3.4) — a `GET /projects/:slug/events?after_seq=` route would make polling lossless and cheap; **start without it** (pure Q7 polling, reads on read-only connection, doc 04 §2.4) and add it only if load demands. No SSE/WS: new server machinery for zero correctness gain; the cursor feed is the only future push-ish upgrade.

## Reuse vs build

**Reuse:** `DataFreshnessManager` + `useSmartPolling` (transport-agnostic — repoint the health signal), all timeline machinery (`AstridBridgeDataProvider` CAS/lost-ack, `usePollSync` gating, `useTimelinePersistence` backoff, 30 s/3 s cadences), `IncomingTasksContext` sweep, React Query keys, kernel gap-free seqs, R2 task-read contract (doc 18 §5).
**Build:** a bridge-health → freshness signal replacing `onRealtimeStatusChange`; delete the postgres_changes channel wiring; new task-status read path per R2 (2 s/10 s), optional events-cursor route; adjust hard intervals 3–5 s → 2 s active/10 s idle per Q7.
**Cut, don't recreate:** bookmarks/keep-both/divergence_log/`timeline_agent_sessions` realtime, cross-device sync — single-writer local makes them dead weight.

## Risks / open facts

- SDK `read_events`/`subscribe_events` are **not a browser surface**: Python-only, file-based legacy store, 0.1 s poll — cannot feed the app [INFERENCE: they read `EVENTS_FILENAME` in the legacy run dir, `sdk/events.py:21-45`, not the kernel `events` table].
- `DataFreshnessManager` freshness currently keys off realtime events; without a bridge-health signal every smart-polled query parks at permanent 15 s degraded.
- `EventAppendService` has no post-commit notify hook (`core/events/service.py`) — any push needs new server code.
- `eventlog/sync_divergence.py` does not exist; the legacy module is `core/timeline/sync_divergence.py`.
- `config_version` 0→1 first-load edge can trip poll adoption (doc 09 §9).
- 2 s polling must stay bounded (R2 limit/cursor, read-only connections) to avoid the doc-14 "polling load" risk against the single writer.
